# Контракты входных данных — этап 2

Контракт — описание того, что означает таблица и какие записи в ней допустимы. Это договор между генератором, SQL-подготовкой и анализом. На этапе 3 созданы полные синтетические таблицы и сохранён отдельный неполный предпросмотр. Проверка файла конфигурации не означает проверки таблиц; перед продуктовым выводом нужны предусмотренные протоколом проверки и анализ.

Один запуск имеет свой каталог данных. В нём таблица users общая для четырёх сценариев, а назначения и события различаются по scenario. Один и тот же user_id может встречаться в разных сценариях, но внутри каждого сценария назначается только один раз. Сценарии анализируются отдельно.

## users — кто участвует

Одна строка — один уникальный пользователь, признаки известны до назначения.

| Поле | Логический тип | Пустое значение | Смысл / ограничение |
|---|---|---|---|
| user_id | Положительное целое, 64 бита | Нельзя | Уникальный идентификатор пользователя |
| platform | Строка | Нельзя | web, android или ios |
| region | Непустая строка | Нельзя | Синтетическая категория региона; список задаётся до генерации |
| is_new_user | Логический, true/false | Нельзя | Новый ли пользователь; не текст "True" |

Ключ — user_id. Пустая строка не является допустимой заменой отсутствующего значения. Признаки не изменяются от варианта карточки.

## assignments — кому что назначено

Одна строка — назначение пользователя в конкретный эксперимент и сценарий. Таблица является полным реестром участников, в том числе людей без контактов.

| Поле | Логический тип | Пустое значение | Смысл / ограничение |
|---|---|---|---|
| experiment_id | Непустая строка | Нельзя | Совпадает с идентификатором протокола |
| scenario | Строка | Нельзя | null, uplift, harmful или broken_assignment; null здесь имя, не пустое значение |
| user_id | Положительное целое, 64 бита | Нельзя | Ссылка на существующего пользователя users |
| variant | Строка | Нельзя | A или B |
| assigned_at | Момент времени с явно заданным UTC | Нельзя | В пределах периода набора [start_at, start_at + enrollment_days) |

Составной ключ: (experiment_id, scenario, user_id). Повтор такого ключа не допускается даже при совпадении остальных полей: повторный заход не создаёт новое назначение.

В broken_assignment ожидаемое правило анализа остаётся 50/50, а генератор назначает B с вероятностью 0.4. Не требуется, чтобы в конкретных строках получилось ровно 60/40.

## events — что произошло

Одна сырая строка — запись зарегистрированного события пользователя. В сыром слое возможны точные копии и события вне индивидуального окна. Допустимость записи и участие события в расчёте метрики — разные вопросы.

| Поле | Логический тип | Пустое значение | Смысл / ограничение |
|---|---|---|---|
| experiment_id | Непустая строка | Нельзя | Тот же тип и значение, что в assignments; для текущего запуска listing_card_v1 |
| scenario | Строка | Нельзя | null, uplift, harmful или broken_assignment; null — имя сценария, а не отсутствие значения |
| event_id | Положительное целое, 64 бита | Нельзя | Идентификатор логического события, уникальный внутри эксперимента и сценария после удаления точных копий |
| user_id | Положительное целое, 64 бита | Нельзя | Ссылка на пользователя с назначением в этом эксперименте и сценарии |
| event_name | Строка | Нельзя | Только search_view, listing_view, contact_created или technical_error |
| event_ts | Момент времени с явно заданным UTC | Нельзя | Время события; включение в метрику определяется индивидуальным окном |
| listing_id | Положительное целое, 64 бита | Зависит от типа события | Идентификатор объявления, обязательный для просмотра объявления и контакта |

### Связь с назначением и объявлением

Событие соединяется с assignments по (experiment_id, scenario, user_id). По этому сочетанию должно существовать ровно одно назначение. Неизвестный пользователь или отсутствие назначения — ошибка данных. Вариант A/B берётся только из assignments; хранить вторую независимую версию variant в events не требуется.

- search_view: открытие выдачи. Первое такое событие создаётся в момент назначения; повторные открытия имеют своё время и новый event_id. listing_id отсутствует, потому что выдача не является одним объявлением.
- listing_view: просмотр конкретного объявления; listing_id обязателен.
- contact_created: контакт по конкретному объявлению; listing_id обязателен. Для учитываемого контакта должен существовать более ранний listing_view того же пользователя, эксперимента, сценария и listing_id в индивидуальном окне.
- technical_error: техническая ошибка пользователя. listing_id может отсутствовать; если ошибка относится к конкретному объявлению, допустим его корректный идентификатор. Ошибка не исключает наличия контакта у того же пользователя.

Неизвестное или пустое event_name нельзя считать корректным событием или молча заменять другим именем. Повторный заход или повторное действие — новое событие с новым event_id, но назначение пользователя остаётся прежним.

### Ключ, точные дубли и конфликты

Ключ логического события: (experiment_id, scenario, event_id). user_id не входит в него: идентификатор события выделяется на весь сценарий эксперимента, а не отдельно для каждого пользователя.

В сырой таблице разрешены точные копии: совпадают ключ и все остальные поля. Очистка оставляет одну запись такого события. После очистки ключ должен быть уникален.

Конфликт — один и тот же ключ при различии хотя бы одного другого поля, например времени, user_id или listing_id. Это ошибка данных, блокирующая вывод до выяснения причины. Нельзя произвольно оставлять первую запись или считать обе независимыми событиями.

### Время и индивидуальное окно

Назначения появляются в [start_at, start_at + enrollment_days суток). Плановый сбор продолжается до start_at + enrollment_days суток + 24 часа. Он позволяет получить полное окно последнего участника. Событие после окончания набора может быть корректным и учитываться.

У пользователя в метрику входят события только из [assigned_at, assigned_at + 24 часа). Правая граница исключена. Сырая запись ровно на этой границе может присутствовать, но не меняет его метрику. Общий период сбора не заменяет индивидуальное окно. В текущей модели событие экспериментального потока до назначения — ошибка данных, как зафиксировано в протоколе.

### Пример корректной цепочки

Общие значения строк: experiment_id = listing_card_v1, scenario = uplift, user_id = 7. В assignments этому пользователю назначен B в 2026-11-15T23:30:00Z. Набор закончился 2026-11-16T00:00:00Z, а индивидуальное окно закончится 2026-11-16T23:30:00Z.

| event_id | event_name | event_ts, UTC | listing_id | Трактовка |
|---:|---|---|---:|---|
| 101 | search_view | 2026-11-15T23:30:00Z | отсутствует | Начало наблюдения, выдача |
| 102 | listing_view | 2026-11-16T00:10:00Z | 501 | Просмотр после конца набора, но внутри окна |
| 103 | contact_created | 2026-11-16T00:12:00Z | 501 | Контакт учитывается: есть предшествующий просмотр того же объявления |

### Независимые примеры дублей, ошибок и границы

Каждый следующий случай рассматривается отдельно на фоне корректной цепочки выше. Это не общий набор строк: добавление конфликтной записи в общий набор блокировало бы анализ всего случая.

| Случай | Дополнительная запись / изменение | Ожидаемая трактовка |
|---|---|---|
| Точный дубль | Полная копия строки 103, включая время и listing_id | Сырая копия допустима; очистка оставляет одно событие; пользовательская конверсия не меняется |
| Конфликт | Тот же ключ строки 103, но event_ts = 2026-11-16T00:13:00Z | Время различается: конфликт, а не точный дубль; продуктовый вывод блокируется |
| Верхняя граница | Новый event_id = 104, contact_created по 501 ровно в 2026-11-16T23:30:00Z | Корректная по форме сырая запись, исключается из 24-часовой метрики; не является конфликтом |
| Другое объявление | Новый event_id = 105, contact_created по 502 в 2026-11-16T00:14:00Z, без просмотра 502 | Некорректная цепочка учитываемого контакта: просмотр 501 не заменяет просмотр 502 |
| Нет идентификатора объявления | Новый listing_view с отсутствующим listing_id | Нарушение обязательности поля для этого типа события |

## Что означает «UTC» для файлов

В JSON настройки времени представлены строками с Z или смещением +00:00. В pandas используются значения с часовым поясом UTC, в DuckDB — TIMESTAMP WITH TIME ZONE. Физические схемы входных Parquet проверяются в [src/prepare_data.py](src/prepare_data.py). Московское время и UTC не смешиваются неявно.

## Граница этапа

Этот документ фиксирует допустимые данные для генератора, SQL-подготовки и статистического анализа. Примеры некорректных записей объясняют проверки, реализованные в коде и тестах. Неполный предпросмотр генератора явно помечен в manifest.json и не заменяет полный набор.
