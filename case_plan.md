# Практический кейс: A/B-тест карточки объявления и аналитический дашборд

**Статус:** исходный план проекта; реализация завершена. Текущее состояние и результаты — в [README.md](README.md).  
**Цель:** портфолио для Avito Analyst Bootcamp, направление «Продуктовая аналитика».  
**Бюджет:** 10–15 часов самостоятельной работы.  
**Формат:** учебная симуляция маркетплейса на синтетических данных. Не является экспериментом Авито и не использует его внутренние данные.

## 1. Продуктовая задача

Представим сервис объявлений. Команда предлагает изменить карточку рекомендации в поисковой выдаче: лучше показать цену, расположение и основные характеристики предложения. Нужно понять, увеличивает ли это долю пользователей, начавших диалог с продавцом, без существенного роста технических ошибок.

- **A:** текущая карточка.
- **B:** новая карточка.
- **Решение:** рекомендовать дальнейшую проверку изменения, отклонить его или признать результат неопределённым.
- **Что покажет кейс:** постановку гипотезы, проектирование эксперимента, подготовку SQL-витрины, статистический анализ, визуализацию и объяснение ограничений.

Это модель принятия решения, а не доказательство эффективности реального интерфейса. В симуляторе эффект задаётся параметрами; анализ должен оценить его по наблюдаемым событиям.

Для основной версии достаточно локального запуска. Redash, Docker, API, оркестратор и отдельный веб-сервис не нужны. Версии зависимостей зафиксировать в момент реализации.

## 3. Протокол: зафиксировать до анализа

Сохранить проект протокола до генерации результатов. Выбор параметров ниже учебный; их нельзя объяснять данными реального бизнеса.

| Параметр | Предлагаемое значение |
|---|---|
| Популяция | Пользователи, открывшие выдачу и подходящие по правилам участия до назначения группы |
| Единица рандомизации и анализа | Уникальный пользователь |
| Назначение | Независимое A/B 50/50, один вариант на пользователя на весь эксперимент |
| Начало наблюдения | Момент назначения при первом показе выдачи |
| Окно результата | Первые 24 часа после назначения, полуинтервал [assigned_at, assigned_at + 24 часа) |
| Основная метрика | Доля всех назначенных пользователей с хотя бы одним contact_created в окне |
| Контрольная конверсия для планирования | 12% |
| MDE для планирования | +1,2 процентного пункта: 12% → 13,2%, или +10% относительно контроля |
| Уровень значимости | 0,05; двусторонняя проверка |
| Плановая мощность | 80% для отличия 12% от 13,2% |
| Практически ценный эффект | +0,5 процентного пункта; отдельный бизнес-порог, не MDE |
| Набор | 14 полных суток; учебный ожидаемый трафик 3 000 пользователей в сутки |
| Созревание | Завершить сбор событий последнего участника за его полные 24 часа |
| Просмотры результата | Один финальный анализ; без досрочной остановки по p-value |

### Расчёт выборки

1. Вычислить размер эффекта для двух долей через `proportion_effectsize`, взять его абсолютное значение.
2. Через `NormalIndPower.solve_power` получить необходимое число пользователей **на группу**, округлить вверх.
3. Показать отдельно выборку на группу, общую выборку и ожидаемый объём за 14 дней.
4. До запуска убедиться, что ожидаемого трафика достаточно. Если нет — увеличить заранее срок набора до целого числа недель и заморозить новый план.
5. После генерации проверить фактически набранные размеры. Недостаток данных отметить как ограничение, не подгонять seed.

Не записывать примерное число пользователей как выполненный расчёт. Мощность 80% относится к проверке нулевого эффекта при заданной альтернативе; она не гарантирует 80% вероятности доказать превышение бизнес-порога +0,5 п.п.

## 4. Метрики и правила их расчёта

### Основная метрика: Contact Conversion Rate

`contact_cr = пользователи с ≥1 контактом за 24 часа / все назначенные пользователи`

Анализировать по исходному назначению — intention-to-treat. Пользователь без просмотра объявления или без контакта остаётся в знаменателе. Десять контактов одного пользователя не превращаются в десять независимых наблюдений.

Рассчитать для B относительно A:

- размеры групп и количество сконвертировавшихся пользователей;
- конверсии;
- абсолютную разницу в процентных пунктах;
- относительное изменение в процентах;
- двусторонний p-value;
- 95% доверительный интервал абсолютной разницы.

### Воронка и дополнительные метрики

Выдача → просмотр объявления → создание контакта.

- Доля пользователей с просмотром среди всех назначенных.
- Доля пользователей с контактом среди всех назначенных.
- Контакт среди просмотревших — только диагностическая метрика: просмотр зависит от варианта, поэтому это не основная причинная оценка.

Считать уникальных пользователей на этапах; обеспечить порядок событий и вложенность этапов. Не выбирать новую основную метрику после просмотра результата.

### Защитная метрика

Доля всех назначенных пользователей хотя бы с одной `technical_error` за 24 часа.

- Контрольная вероятность в генераторе: 2%.
- Допустимое ухудшение: не более +0,5 п.п.
- Рассчитать разницу B − A и её 95% доверительный интервал.
- Верхняя граница ≤ +0,5 п.п.: в рамках выбранного критерия защитная метрика пройдена.
- Нижняя граница > +0,5 п.п.: есть свидетельство недопустимого ухудшения.
- В остальных случаях безопасность по этому критерию не подтверждена.

Не считать отсутствие значимого ухудшения доказательством безопасности. В кейсе защитная метрика техническая; качество лидов и выручка не измеряются.

## 5. Данные и симулятор

### Входные таблицы

| Таблица | Поля | Назначение |
|---|---|---|
| users | user_id, platform, region, is_new_user | Признаки, известные до назначения |
| assignments | experiment_id, scenario, user_id, variant, assigned_at | Полный реестр назначений, включая пользователей без целевого события |
| events | scenario, event_id, user_id, event_name, event_ts, listing_id | События выдачи, просмотров, контактов и технических ошибок |

Для полей назначений задать уникальность `(experiment_id, scenario, user_id)`. Идентификаторы событий уникальны внутри сценария. Все даты привести к UTC. Реальных персональных данных нет.

### Простейшая модель воронки

- Каждый участник получает событие `search_view` в момент назначения.
- В A вероятность хотя бы одного `listing_view` — 60%.
- Среди просмотревших вероятность контакта — 20%: целевая конверсия A равна 12%.
- В сценарии эффекта вероятность просмотра в B — 66%, условная вероятность контакта — 20%: целевая конверсия B равна 13,2%.
- Генерировать события в порядке: назначение/выдача → просмотр → контакт. Контакт возможен только после просмотра в том же окне.
- Повторные просмотры/контакты разрешены, но пользовательская витрина сворачивает их в бинарные признаки.
- Техническую ошибку моделировать отдельным событием на уровне пользователя.
- Для проверки очистки добавить небольшую долю точных дублей событий с тем же event_id.

Можно добавить одинаковую для A и B сезонность потока по дням недели. Не усложнять базовую версию моделированием аукциона, продавцов и многопользовательских взаимодействий.

### Четыре сценария

| Сценарий | Что задать | Как должен вести себя анализ |
|---|---|---|
| null | A и B одинаковы: 12% контактов, 2% ошибок | Оценка колеблется вокруг нуля; отдельный запуск может дать ложноположительный результат |
| uplift | A: 12%, B: 13,2%; ошибки 2% в обеих группах | Оценить эффект и неопределённость; не гарантировать заранее значимость |
| harmful | Конверсии как в uplift, но ошибки B — 4% | Не рекомендовать изменение при нарушении защитного критерия |
| broken_assignment | План 50/50, но фактическое назначение 60/40 | Обнаружить SRM и заблокировать продуктовый вывод |

Общий seed, например 42, и параметры сценариев сохранить в конфигурации до анализа. Использовать воспроизводимые независимые потоки случайных чисел. Не перебирать seed ради красивого результата. Ничего не записывать в итоговый отчёт как «полученный эффект», пока анализ не выполнен.

## 6. SQL-витрина и контроль качества

Разделить SQL минимум на три понятных шага:

1. **Очистка событий.** Удалить только точные дубли; один event_id с разным содержимым считать ошибкой данных. Не удалять записи без объяснения причины.
2. **Витрина на пользователя.** Начать с assignments, присоединить users и через LEFT JOIN события в пределах окна. Условные агрегации формируют флаги `has_listing_view`, `has_contact`, `has_error`.
3. **Агрегаты.** По сценарию, варианту и дню назначения получить число участников, суммы флагов, конверсии и воронку. Деление выполнять в вещественном типе.

Использовать CTE, JOIN, CASE и агрегаты. Оконную функцию ROW_NUMBER можно применить для удаления дублей; важно понимать её назначение, а не добавлять ради списка технологий.

Обязательные проверки:

- одна группа на пользователя, нет потери участников относительно assignments;
- нет неизвестных пользователей, пустых ключей и неизвестных типов событий;
- события не предшествуют назначению;
- все участники основной выборки имеют полное окно наблюдения;
- контакт не возникает без предшествующего просмотра;
- SQL-метрики совпадают с независимым контрольным расчётом на небольшом примере;
- точный дубликат события не меняет пользовательские метрики;
- численности и конверсии рассчитаны отдельно по сценариям, без их смешивания.

Пользователей с незрелым окном не исключать постфактум из одного варианта: завершить сбор по плану либо явно признать запуск незавершённым.

## 7. Статистический разбор

### Проверка распределения по группам — SRM

По полному реестру назначений сравнить наблюдаемые количества A/B с ожидаемыми 50/50, используя критерий хи-квадрат.

- Заранее выбрать порог SRM p-value < 0,001.
- SRM проверяет проблему распределения/сбора, а не полезность изменения.
- При срабатывании показать диагностику, но не выдавать рекомендацию о внедрении.
- Проверить распределения platform и is_new_user как диагностику. Баланс по нескольким признакам не доказывает корректность всей рандомизации.

### Основная проверка

Для достаточно больших групп и достаточного числа успехов/неуспехов использовать двусторонний z-тест двух независимых долей: `proportions_ztest`. Для интервала разницы — `confint_proportions_2indep`, метод `newcomb`, сравнение `diff`, порядок B, затем A.

Явно проверить применимость приближения. В редких сегментах не переносить автоматически тот же тест. Основной вывод делать по всей заранее определённой популяции.

Тест и интервал используют разные приближения и у границы значимости могут слегка расходиться. Зафиксировать методику заранее, не выбирать после расчёта удобный результат; пограничный случай описать как неопределённый.

### Правило решения

1. Ошибки качества данных, незрелые окна или SRM → **результат недостоверен / анализ остановлен**.
2. Нарушен защитный критерий или безопасность не подтверждена → **внедрение не рекомендовать**, даже при росте основной метрики.
3. Для положительной рекомендации нужны положительная статистическая оценка (p < 0,05, оценка B − A > 0) и нижняя граница 95% интервала основной разницы выше бизнес-порога +0,5 п.п.
4. Если интервал включает ноль или практически важные альтернативы → **данных недостаточно для уверенного решения**.
5. Если верхняя граница эффекта ниже бизнес-порога → **практически важный выигрыш не подтверждён**.

Текст рекомендации формулировать для симулируемого продукта: «основания для следующей проверки/ограниченного запуска», а не «доказан рост бизнеса Авито». Продление реального теста после просмотра p-value потребовало бы нового плана; в этом кейсе автоматического продления нет.

## 8. Дашборд

Один HTML-файл, открывающийся без Python-сервера. Заголовок постоянно сообщает: «Учебная симуляция, синтетические данные». При экспорте включить Plotly в HTML, чтобы файл работал без CDN.

**Минимум четыре блока:**

1. **Паспорт эксперимента:** сценарий, сроки, размер групп, зрелость окон, SRM-статус.
2. **Воронка A/B:** число пользователей на этапах и доли от всех назначенных; явно подписать знаменатели.
3. **Эффект:** конверсии, разница B − A и её 95% интервал; вертикальные линии нуля и бизнес-порога +0,5 п.п.; рядом защитная метрика.
4. **Динамика:** число назначений и конверсия по дню назначения с полными окнами наблюдения; пометка «диагностика, не основание для досрочной остановки».

Переключатель четырёх сценариев должен согласованно обновлять графики, показатели и рекомендацию. Если это не укладывается по времени, допустимы четыре самостоятельных HTML-отчёта с единым оформлением.

Признаки удачной визуализации: одинаковые цвета A/B на всех графиках, подписи единиц, различение процентов и процентных пунктов, отсутствие обрезанной шкалы, преувеличивающей эффект. На графике воронки не выдавать отношение контактов к просмотрам за эффект среди всех назначенных.

## 13. Ограничения, которые нужно уметь объяснить

- Поведение и истинный эффект заданы симулятором; переносимость на реальный маркетплейс не проверяется.
- Базовая модель предполагает независимость пользователей; взаимодействие покупателей и продавцов может нарушать это в настоящем эксперименте.
- Технические ошибки — лишь один защитный показатель; качество контактов, жалобы, нагрузка продавцов и долгосрочные эффекты не покрыты.
- Учебные baseline, MDE и пороги не выведены из экономики реального продукта.
- Небольшой p-value не равен большому бизнес-эффекту, а большой p-value не доказывает равенство вариантов.
- Этот кейс демонстрирует владение методом, а не коммерческий опыт.
